# Four Years, Four Rewrites: Building a Cascade CMS Library

## Prologue

This is the history of a project that started as a low priority intern assignment and slowly turned into something much bigger: a typed, async Python client for Cascade CMS's REST API, plus a skill package that lets AI agents write scripts against it. The story runs through four distinct eras, an inherited image optimization script, the birth of a standalone API library, that library looping back into the script that spawned it, and finally a ground up redesign built on Pydantic. Along the way there are some recurring lessons: that documentation matters as much as code, that architecture has to be allowed to change shape more than once before it settles, that breaking changes are sometimes the kindest thing you can do for your future self, and that planning debt (the cost of not mapping things out up front) has a way of showing up again and again across years, in different disguises. This is also, in part, a story about learning how to use AI as a collaborator rather than a shortcut, and about being honest with myself when something I built didn't work the way I wanted it to.

## Chapter 1: The Inherited Script

I was a newly hired intern at the College of Southern Idaho, and this project was handed to me as a low priority assignment, mostly a chance to show I could actually write Python. Two other people had touched the script before me. One of them wrote the original version, and the next person fixed some of the errors that were left behind. By the time it reached me, the repository had been quiet for a while, sitting at `800c987` (2023-01-27), a small fix, since 2023.

What slowed me down wasn't really the code. It was the documentation. Everything lived in Notion pages that read like a novel instead of something you could quickly reference, and worse, it was locked behind Notion itself, so there was no fast way to check anything. Between that and a codebase that split its logic strangely across two languages, a Node.js script driving an interactive terminal experience, which then called out to a separate Python script to actually talk to the REST API, I decided the whole thing needed to come together. There was no real reason a script this simple needed two programming languages when Python alone could do everything.

That's the motivation behind the consolidation commit, `f0aef49` (2025-04-01), which collapsed the old Node wrapper and four separate Python modules (`config_variables.py`, `cascade_api.py`, `optimize.py`, `optimize_image.py`) into a single file. Looking back at the old Notion docs now, I can see the original intent clearly: JavaScript was meant to orchestrate the Python logic. Later on, I'd replace that whole idea with Docker containers instead.

At first the goal wasn't improvement so much as clarity. The original project effectively had two separate command line entry points, one in the Node script and one buried in `config_variables.py`, and untangling that was most of what the consolidation effort was actually about. It also meant I could see every function I needed without chasing it across four files. I didn't have any real complaints about the Python logic itself, with one exception: every Cascade template in the script was built by hand, with surgical logic required just to pull the values you needed out of the response. That single frustration is what eventually sparked the idea of building a real library.

A few concrete examples of what that pain actually looked like: the script verified the API key by hitting a `readpreferences` endpoint, which wasn't a bad idea for basic verification, except Cascade returns an error regardless of which endpoint you call if something's wrong, so the choice of endpoint barely mattered. Every other endpoint was built by hand inside `cascade_api.py`, string by string, when something like a proper `edit()` method could have handled it. And the most common annoyance of all was object traversal. Cascade wraps every response like `{"asset": {"<asset-type>": {...}}}`, which meant writing things like `get_data_object()["asset"]["folder"]["children"]` just to reach a value that could have been accessed like an attribute, `asset.children`, instead of a chain of nested brackets. That same pattern, identifiers wrapped in their own `["path"]["path"]` structure, is something I'd eventually address directly in the library itself.

Later, in my own fork of the optimization script, I split the functionality back into two Python files, but this time along a different seam. `optimizer.py` became the entry point, bundling together the CLI and interactive experience. Both had different ways of gathering input from the user, but they fed the same information into the rest of the program, which is why they got their own classes rather than their own files. `optimization_process.py`, meanwhile, grew out of the old `optimize_image.py` logic and became its own scope entirely. The re-split wasn't just consolidation for its own sake, it was dividing the script along front end (credentials, user interaction) and back end (reading and processing images) lines. And once the library matured enough to take over the heavy lifting, my fork ended up with roughly half the Python code it used to carry.

## Chapter 2: Birth of the Library

The fork went quiet for about fifteen months after `be43741` (2024-02-07), a "backup before reformat hard drive" commit, which is the last thing that happened before I picked it back up on my own with `51314dc` (2025-05-12).

At the time, adding an async driver wasn't strictly necessary. But I kept asking myself: what if I wanted to read five hundred assets at once? The synchronous approach doesn't scale well for larger reads and writes, and even though time wasn't a real constraint for the image optimization script itself, I could already picture a bigger script grinding through blocking code forever while I tried to debug it.

Building a whole second, parallel package (`cascadecmsdriver_async/` alongside `cascadecmsdriver/`) was really an experiment. My reasoning at the time was simple: use the sync method for a quick script, and the async one if you're working with a lot of assets at once. That framing got reworked later, but at the time it felt reasonable, and my instincts kept nudging me toward the async side more and more, which is why I slowly phased the sync version out over the following months. I never really considered just making the sync methods optionally awaitable, mostly because of that sync-versus-async use case split I'd talked myself into. I also went back and forth between two designs: should the whole library be async, with the end user awaiting every function themselves, or should there be a synchronous control panel on top with the async logic hidden underneath? Looking back, that entire exploration phase, messy as it was, ended up shaping the library I have now.

When I actually opened the code, `cmstypes.py` was essentially blank. I don't know if that was intentional or just abandoned, but either way, it meant the library wasn't usable yet, so I started writing my own types. Those early types still form the backbone of the library today. It wasn't until after I'd already built a chunk of them that I realized the old approach had actually been built around WSDL and SOAP, a completely different way of talking to Cascade than the REST API I was working with. That's when I went looking into the `zeep` library to understand what I'd stumbled into. My own types ended up far more compact than the old `cmstypes.py`, which had mapped out every WSDL signature without any real understanding of what shape the REST API itself actually returned. For testing, I leaned on the image optimization script as a real world proving ground.

The `wrapper.py` rework (`5c9dd25`) shipped with its own commit message admitting it wasn't finished, "needs refactoring and more testing." That was really just a checkpoint for myself. Looking back, my commit hygiene wasn't great during this stretch, which is part of why there are so many commits in the first place, I was iterating fast and trying things out. If I were doing it again, I'd keep commit messages short and direct, something like "Added wrapper.py," and leave any side notes in a message to myself or a dedicated TODO list instead of burying them in the commit history. Around this same time, `edit()` had no real error checking on its results until `1a852a6` came along and fixed that. In a fast paced collaborative environment with other contributors, that gap could have caused real problems. Since I was the only one running the script and building the library at the same time, it mostly went unnoticed, but it wasn't good practice, and I'll own that as negligence rather than pretend it was a deliberate choice.

The shared types moved through three different homes before settling. They started inside `wrapper.py`, moved into an async only module during that phase of slowly drifting away from the sync code (I kept the sync version around just in case), and then moved again into a shared `src/cmstypes.py`, reached at first through a `sys.path.append` hack so both sync and async versions could use it. The final move properly exported the module through the wheel itself. Some of that churn also came from figuring out packaging. My first official iteration used `setup.py`, which has since become a deprecated way of building distributables, and the difference between those last two commits really just shows me struggling to get that part working.

The name `CascadeWrapperBase` is a holdover I probably should have dropped by now. At the time, "Base" implied I was planning to build CLI functionality on top of it later, extending the wrapper interface. Really, what I needed was a context manager that held a reference to the operations and the driver, something multiprocessing logic could theoretically hook into as well. It wasn't the cleanest naming decision, but it stuck.

The `CachedSession` saga was its own strange detour. I ran into weird syntax highlighting behavior in VS Code, it couldn't seem to recognize `SQLiteBackend`, and I ended up suspecting the brackets around `allow_methods` were the real culprit, though at the time I chalked it up to an import error and changed things accordingly. I never actually pinned down the real cause; it just seemed to start working again once both changes were in place. The commit message claiming the error "can be ignored" was misleading in hindsight, the actual fix quietly stopped wiring the cache configuration into the session at all, which meant caching was silently disabled for a while. Even now, running the library without caching enabled feels noticeably slower. I've never actually hit a rate limit, but the value is very situational, caching makes the biggest difference when you're mapping out site structures with deep, nested folders, since you can cache folder assets and make traversal much faster. Other times, when you specifically need fresh data, that same caching behavior works against you.

Right around the point where that bug lived, an experimental `WIP` branch split off and kept going on its own, building out a real `CascadeObject` and context manager support that never made it back into `main`. It wasn't a fully thought out decision to branch off there, it was more of an experiment that never got closed out. Around that same time I received new feedback, the code review that would eventually push me toward the Pydantic rewrite, and I made the call to set the old version aside rather than finish reconciling `WIP`, since the leap to the new architecture felt like too major a shift to bother merging old exploratory work into first.

`CascadeObject` itself came from wanting a single, unified type I could plug directly into the driver's fetch function, mostly for the sake of type hints. I liked the idea of one generic type that could represent both payloads and asset types alike, instead of a long chain of piped union types. That class has since been dropped entirely in favor of a much lighter `TypeAlias` version of `CascadeObject`, which does the same job without the overhead of a full class.

If there's a broader theme to this whole era, it's the challenge of building your own REST client on top of an API that has its own baggage. Cascade's REST API feels like a bandaid over its older WSDL and SOAP based mechanism. Testing it directly with API tools made that obvious pretty quickly: Cascade doesn't really use proper HTTP status codes at all. It returns 200 almost no matter what happens, and leans entirely on the user to read the actual success or failure out of the JSON body itself.

## Chapter 3: Birth of the Library (continued)

The commit that first vendored the wheel into the optimizer, `14c2f4f`, replaced the script's raw `requests` calls with the library's driver. But the real starting point goes back further than that. The optimizer's own `CascadeWrapper.py` and `APIHandler`, back when they still lived inside the script itself, were the first unofficial versions of what would become `cmstypes.py`, `driver.py`, and `wrapper.py`. That was ground zero: early prototypes with crude manual validation and hand built templates. The original idea was modest, just a thin, lightweight wrapper around Cascade's quirks. As more features got added, that wrapper eventually had to move into its own repository, `py-cascade-cms-old`, which is the point where the wrapper and the library properly merged into one thing.

It worked surprisingly well early on. In `dca1198` I started replacing hardcoded test values with real parameters, and put together the first real pipeline: `jsonToIdentifier()` converting search results, which are really just references rather than full assets, into identifiers, followed by a step turning that identifier into the actual asset. There was a lot of trial and error involved, working out request shapes against limited documentation using API testers like Postman and later Bruno. That same trial and error process ran throughout the work on `cmstypes.py`.

Around this point I also split `optimizer.py`'s single `Prompter` into `AppMode` and `CLIMode`, and quickly let `CLIMode` fall dormant. That wasn't an accident so much as a priority call, I didn't want to take on the burden of maintaining both the interactive and scripted paths at once, and the interactive experience felt like the higher priority of the two. The old `Optimization(APIHandler)` class stuck around commented out, not out of sentiment, but because it was a genuinely useful template during that reorganization, holding the exact image processing logic from Chapter 1's codebase, ready to copy into whatever its next home turned out to be.

There's a road not taken worth mentioning here too. Around this same early stage, I seriously considered a completely different direction: an existing JavaScript library, [Cascade-CMS-API by kuklaph](https://github.com/kuklaph/Cascade-CMS-API), that already handled the Cascade REST API. If I'd gone that way, I could have ported everything over to JavaScript and dropped Python entirely, and honestly, in a faster paced environment where burning energy reinventing the wheel doesn't make sense, that would have been the more sensible choice. But I took this internship as an opportunity to build my own API library from the ground up on purpose, because I wanted the experience of understanding what actually goes into building a standalone project. Script writing alone isn't a particularly in demand or marketable skill on its own, but the problem solving and design experience that comes from building a real piece of software is.

The commits around `aa300b5` and `052a52f` mark a real separation of concerns. The wrapper's logic moved into a distributable package, and the script itself moved a step closer to the two file structure it has today, with the wrapper now living in a binary rather than inline code. This stretch focused mostly on basic CRUD operations, while workflow and admin related operations were set aside for later. By the time `052a52f` landed, preparing the ground for a full CLI implementation, it genuinely felt like real progress, like I finally had the real estate to build the front end properly.

Some of the trickier debugging from this stretch is only clear in hindsight. The cache issue traced back to a wheel built from `5bb45af`, a commit on the old `py-cascade-cms-old` `WIP` branch, that bumped the version straight to 1.4.5, overshadowing 1.4.4 before I'd even fully tracked what changed between them. The actual fix ended up being simpler than expected: the cache config's filename needed to exclude its extension, otherwise the caching library would append its own `.sqlite` suffix on top, producing something like `cache.sqlite.sqlite`. What still puzzles me looking back is that `close_connection()` doesn't even exist as a function signature in `5bb45af`, only an early `close()` implementation for the context manager. My best guess is that the closing behavior did work at that stage, and the function was simply renamed later, `close_connection()` being a remnant of the older manual connection closing logic from version 1.4.4.

A lot of that debugging leaned on running the script locally alongside manual Postman calls, walking through the same pipeline the program itself would follow. That combination helped a lot. But Docker introduced its own complications: depending on whether the script ran locally or inside a container, working directories and cache file locations came out slightly different, which caused instability that lingered for a while. I did leave a comment about it at the time, but looking back, that whole workaround created more hassle than it was worth. If I could do it again, I'd fully build and test the script locally, make sure it was genuinely production ready, and only then migrate it into a container, rather than debugging through Docker logs, which is close to the last place I'd want to debug anything. On top of that, there was no default cache configuration set at all, which only added to the instability.

The `date` versus `datetime` bug that showed up in `getProcessTime` might have been caught earlier with proper type hints, but the program stayed loosely typed through this whole stretch, and honestly, I didn't think about it too much at the time. My reasoning back then was that type related friction felt cosmetic and distracting, and I didn't want to write an ignore clause without a solid reason, or deal with the extra overhead of importing types everywhere. Looking back now, I'd keep type hints from day one, if only because they force you to keep asking, "what type does this function actually need," and "why this type instead of another." Those are the same deeper design questions I picked up from working in strictly typed languages like C++ and Java, and it's a habit that needed more polishing over time than I gave it credit for.

The branch history around this point gets messy. I accidentally committed environment variables that should have been ignored more than once across these commits. Docker showed up a couple of commits in, and not long after that, I split CLI and interactive modes apart for good in `14c2f4f`, which is also where the actual library first got wired into the script, `APIHandler` fading out in favor of what would become the library's own wrapper. At that early stage, only the driver and the CMS types really existed, and both treated data in a fairly primitive way. Between `dca1198` and `052a52f`, the script stopped relying on the local `CascadeWrapper` I'd been using to test, and by `052a52f` that file was fully orphaned, no longer referenced anywhere, right before the merge that also folded in the optimize logic split. All of that happened between April and May.

Starting in June, the `dev` branch picked up the async work in earnest, bumping the library from 1.2 and 1.2.2 up to 1.2.4, with noticeably stronger use of type hints throughout. Testing against that branch surfaced one particularly interesting quirk: a `siteName` search parameter that wasn't documented anywhere, but that let you narrow results down to a specific site. Looking back, `WIP` and this branch both ended up feeling like artifacts left behind more than deliberate long term experiments. I don't think I misused the branch exactly, but the commit messages could have been a lot better. Because they never generalized what actually changed, backtracking through them later was genuinely difficult. If I went back and redid it, I'd want that first branch commit to say something as simple as "async implementation for the branch," and in general, I'd be far more intentional about commit messages, especially at the moment a branch splits off.

The dry run mode that closes out this era, `REPORT_MODE`, came from a specific need: testing upload behavior safely against production servers. Up to that point, I'd only ever worked against the development server, where the risk of breaking something was low. That's exactly why dry run mode didn't show up sooner, and why it finally did once I felt the script was genuinely ready to be tested against production, since I wanted a way to see what would actually change before anything touched a live server. Making `REPORT_MODE` a required environment variable rather than something with a default followed a philosophy I was already leaning toward: keep arguments and configuration out of hardcoded values in the program itself, and push them into environment variables or config files instead. That same philosophy carries through into the current library today. The broad exception handling from this stretch was very much a product of where the library was at that point in its life, still in its infancy. Around this same time, I also cleaned up the manual pixel manipulation logic, replacing it with a proper `numpy` implementation instead.

## Chapter 4: Ground-Up Redesign

The rewrite itself came out of a code review. By that point, all of my validation and parsing was still being done by hand, and the reviewer recommended a library called Pydantic to handle it properly. I agreed. Even though the underlying concept of the library stayed the same, adopting Pydantic meant the architecture needed a serious overhaul, and that, combined with a structural suggestion from the same reviewer, is what ultimately led to starting a new repository instead of continuing to patch the old one.

That structural suggestion was to flatten the repo, dropping the `src/`-style layout in favor of what the reviewer called a more common, pythonic convention. I actually looked into it myself before deciding. What I found is that a flat layout tends to suit quick prototypes, small scripts, and minimal local setups well, but a `src/`-layout is generally the better choice for actual libraries, production packages, and anything that needs to run through CI/CD pipelines, which this project would. Even with a relatively small number of files at that point, the complexity of what I was building meant I needed a structure that could scale as new features came in. So I kept the `src/`-layout on purpose. It's worth noting that the original decision to use `src/` back in the very first rewrite wasn't really a considered architectural choice at all, it was just a habit carried over from my experience with JavaScript. This time, keeping it was deliberate, backed by actual research rather than instinct.

The `OperationChain`/`ChainGroup` design went through its own back and forth. A batched approach worked well for simple calls, reading five hundred assets at once asynchronously, for example, but it didn't fit the chaining philosophy I'd envisioned for the project, which was inspired by JavaScript's promises. The real problem was traceability. When something went wrong inside a batch, it became hard to tell whether the failure was something I'd caused or something Cascade itself didn't like, and that ambiguity showed up constantly while debugging. Passing the results of one function into another was awkward too. That's what pushed me toward per-identifier chains instead, one independent chain per asset, with `.then()` callbacks now receiving a single `Asset` rather than a list.

That was a breaking change, but a necessary one. It's also why the design now accepts an explicit `executor` argument for CPU intensive workloads, and leans harder on clear type hints generally. Forcing the end user to be specific leads to better script design on their end, rather than more confusion or unchecked assumptions. The skill package built on top of the library is dynamic enough to adapt to whatever shape the project takes, so the underlying wrapper philosophy hasn't changed in any fundamental way here, it's just shifted where the boundaries sit.

The `edit()` method lost its identifier argument entirely in this redesign. The old hand rolled version used to guess the asset type from a second nested field in the response, which turned out to be unreliable once the `OperationChain`/`ChainGroup` shift exposed the cracks in it. It also turned out that `edit()` never actually needed the asset type in the first place, so that whole piece of logic wasn't just broken, it was unnecessary to begin with.

The idea that Pydantic models could serve as both serializer and deserializer wasn't a brand new realization in this era, it clicked earlier, while designing `py-cascade-cms-old`, once I noticed how closely Cascade's payload shape mirrored its response shape. What Pydantic added was bundling validation and serialization into a single model, which turned out to be exactly the fit this library needed. Some of that understanding came from Cascade's own documentation, but a good deal of it came from noticing the same patterns repeat across trial and error testing. Those validation containers, things like `SearchInformation` and `NewAsset`, exist specifically to shield users from Cascade's more common complaints, "you don't have this field," and from quieter quirks that don't produce an error at all. The `siteName` parameter is a good example: it can be left out entirely without Cascade raising any error, but doing so makes a search unreliable, since it silently searches across every site instead of the one you meant. That was a genuinely confusing puzzle to work through during testing, and AI assistance ended up being a real help in mapping out the rest of Cascade's payload behavior without needing to run down every quirk by hand.

The skill package itself grew out of a specific frustration. Before the library matured, I was still writing one-off scripts directly against `requests`, and the underlying design kept shifting out from under me on short notice. At some point that turned into a real question: why invest time and energy into a script when the entire logic behind it might change again soon after? That frustration is what pushed me toward building a skill package, a way to describe what behavior a script should have and let an agent implement it on top of the library. The value is mostly efficiency: letting an agent handle the core implementation frees up my own time for other projects, while the library underneath stays human readable, so I can still edit it directly without needing an agent involved. It's a hybrid, collaborative approach rather than a fully automated one.

Building and then dropping the "lite" version of that skill taught me something concrete about the real limits of smaller, flash tier models. That whole detour started from curiosity: could a cheap, effectively free agent still produce genuinely usable code? Pushing those models past their comfortable limits was interesting, but the honest conclusion is that trying to optimize or chain together smaller models to approach the quality of larger ones isn't worth the effort, even where it's technically feasible. Current models simply aren't mature enough for flash tier or local open weight setups to reliably serve as script writers on their own, and the kind of deep model tuning and workaround engineering that would be required to close that gap is well outside the scope of what I'm actually trying to build. The discovery process itself was still worth going through, even if the practical answer ended up being no. The local model side of that exploration stayed purely speculative, since running those models at a useful scale would require commercial grade hardware I don't have and can't justify funding just to satisfy curiosity.

Setting the skill package aside entirely, the library on its own has been genuinely useful. Being able to call operations cleanly, the way you would with any other SDK, has cut down enormously on time spent debugging Cascade's odd behavior separately from debugging my own actual mistakes. Without it, I'd still be rewriting the same parsers and chasing the same quirks over and over, instead of focusing on the logic of whatever script I was actually trying to write.

If there's one mistake that threads through every chapter of this story, it's how much time got lost to design changes that could have been avoided with more upfront planning. That shows up early, in the churn around distributing the first wheel files, and again later, in the shift from batched operations to individual chains. The idea behind `.then()` was actually in my head from very early on, but it didn't get properly implemented until much later, which meant more rework down the line, even with an agent helping carry some of that load. There's a second version of the same mistake too: adding caching before I really understood how the library would be used, only to grow uncertain later about whether it was solving a problem that actually existed yet. Looking back, mapping out the logic more carefully up front, with AI assistance from the very beginning, could have answered a lot of the "what if" questions early enough to weigh which features actually mattered most before building them. It's been a useful lesson not just about architecture, but about how to use AI well, especially for planning rather than just execution.

As the library nears its final stretch, the scope has grown well past a simple API library, partly because my own use of AI agents has picked up so much recently. With AI tools maturing quickly, it felt like the right time to experiment, and that experimentation ended up expanding the project in a direction I hadn't originally planned for: building out an MCP server to extend what the script writing skill package can do. Instead of an agent writing scripts blind, it can now reference real data from a live Cascade instance, giving it better context and, in turn, leading to better script designs. There are still a few structural changes left before I'd call this project truly polished and finished, but it's come a long way from a low priority intern assignment meant to prove I could write Python.
