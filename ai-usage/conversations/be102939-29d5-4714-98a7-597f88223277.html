The person works with a single `CascadeCMSRestDriver` instance and wants the library to be usable by end users who create separate scripts for varying tasks. The core technical problem addressed was a class-level state mutation bug (`CascadeCMSRestDriver.post_process`) causing race conditions, combined with sequential synchronous callback execution blocking the event loop. The refactor introduced instance-level callback storage (`_callbacks: list` on the `Operations` dataclass), a fluent `.then()` method returning `Self`, and async-safe callback execution via `_execute_callbacks_on_result()`. The callback API was extended to support both single callbacks and lists: `.then(func)`, `.then([func1, func2])`, or chained `.then(func1).then(func2)`. The person confirmed that error handling should log and continue to the next callback rather than stopping execution. A significant design discussion centered on executor strategy for mixed workloads. The person's use cases include I/O-bound callbacks (page structure editing, asset manipulation) and CPU-bound callbacks (image optimization from base64-encoded data). After discussing four options—always ThreadPoolExecutor, user-specified executor, auto-detection, and two-pass design—the person confirmed they want end users to specify the executor at the `submit_requests()` call site, preferring flexibility with a simple interface and sensible defaults. The recommendation was `ThreadPoolExecutor` as default (safe for I/O) with optional `ProcessPoolExecutor(max_workers=cpu_count())` for CPU-bound work passed as `executor=` parameter, yielding approximately 8× speedup on an 8-core CPU (25 seconds reduced to ~3 seconds for 500 image optimization callbacks). A key constraint noted was that `ProcessPoolExecutor` requires module-level functions due to pickling requirements—lambdas and nested functions are not serializable to worker processes. The conversation concluded with the person asking for clarification on whether requests are processed individually, which was confirmed: each of the 500 HTTP requests is sent individually but concurrently (capped at 50 via `asyncio.Semaphore`), and each result flows individually through the callback pipeline, with all 500 results processed in parallel via `asyncio.gather` while maintaining sequential callback order per result.
