Conversation overview Keith is building a read-only MCP (Model Context Protocol) server for Cascade CMS to improve script-generation accuracy in his `cascade-cms-script-writer` skill. The core problem he identified is that the existing skill relies on static schema documentation in a `skills/` folder, causing agents to guess at field names and structures. By giving the agent live read access to a real Cascade server, it can inspect actual asset schemas, folder structures, structured data node groups, and page configurations before generating scripts, producing far more accurate output. The conversation covered the full design lifecycle: security architecture (MCP vs CLI, settling on MCP for credential isolation), tool specification (six read-only tools: `cascade_search`, `cascade_read_asset`, `cascade_get_data_structure`, `cascade_get_page_config`, `cascade_root_container_id`, `cascade_list_sites`), token-efficiency patterns (concise/detailed response modes, scalar-vs-container collapse rule for `cascade_read_asset`, progressive disclosure), and distribution model. Keith inspected his existing `py-cascade-cms` library (`cmstypes.py`, `operations.py`) to confirm the `Asset` class already has the necessary helper methods (`get_data_structure`, `get_page_configuration`, `root_container_id`) and that `search` returns `IdentifierType` objects (id, asset_type, path/siteName — no title field). The MCP wraps these existing methods rather than reimplementing them. Keith also confirmed the skill files should be kept alongside the MCP since they serve different purposes: MCP provides live grounding, skill provides generation mechanics and static validation via `validate_script.py`.
