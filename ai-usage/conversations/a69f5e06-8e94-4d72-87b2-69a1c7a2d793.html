`_ASSET_TYPE_KEY_ALIASES` has predefined keys because **Cascade's REST API has hard-coded exceptions to its normal naming convention that can't be derived programmatically**. Here's what's happening: 1. **Normal pattern**: When you request an asset of type `"format"`, Cascade wraps the response under a re-cased key like `"format"`. This is predictable and mechanical. 2. **The exception**: For script formats (`format_SCRIPT`), Cascade responds with the wrapper key `"scriptformat"` instead of the expected `"format"`. This is a hard-coded quirk of the API server. 3. **Why it's predefined**: Rather than guess at patterns or assume all responses follow the re-casing rule, the library uses a **"don't guess" discipline** (as noted in the comments at cmstypes.py:604-607 and references.py:26). This means: - Only map what's been **confirmed via actual Cascade payloads** - Make exceptions explicit and visible in the code - If a new exception is discovered, add it to the dict rather than inferring a rule - This keeps the behavior predictable and prevents silent bugs from wrong guesses So the predefined entries aren't an arbitrary choice—they're a defensive pattern against Cascade's undocumented API quirks. You document what you know works, and nothing else.

You raise a fair point—there's a design tension here. The current approach centralizes the normalization problem in the `Asset` class to provide a seamless interface. But you're right that it couples library code to Cascade API quirks. A few options to consider: **Option 1: Remove normalization entirely, expose raw keys** - Strip `_ASSET_TYPE_KEY_ALIASES` and just use `_asset_type` as-is - The caller sees exactly what Cascade returns - Pro: lighter, no magic, explicit responsibility - Con: caller code has to handle "scriptformat" vs "format" inconsistency **Option 2: Fail fast on unknown wrapper keys** - Validate that the response wrapper matches expected re-casing when creating an Asset - Raise a `CascadeError` or similar if it doesn't - Pro: explicit failure mode, caller sees the problem immediately - Con: might break on legit Cascade responses we haven't documented yet **Option 3: Move normalization to a separate decorator/factory** - Keep Asset simple (just hold the raw data) - Have a separate `normalize_asset()` function callers can optionally use - Pro: Asset stays lightweight, normalization is opt-in - Con: extra boilerplate for callers who want normalized types **Option 4: Make it configurable** - Add a parameter to Asset.__init__ to control whether to normalize - Callers can choose lightweight or normalized versions Which approach aligns better with how you want the library to behave? My gut is **Option 2** (fail fast) might be cleanest—let Cascade's inconsistencies bubble up as explicit errors rather than silently normalizing them away.
